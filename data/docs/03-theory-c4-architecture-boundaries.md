# Теория — C4 и архитектурные границы

> Все кейсы E-commerce Checkout и Payment Processing ниже — **fictional / illustrative cases** курса «I Am Lead». Это учебные модели, не являющиеся описаниями реальных систем или продуктов.

---

## 1. Зачем нужен C4: преодоление хаоса диаграмм

В архитектурных обсуждениях часто рисуют схемы, которые не помогают, а запутывают. В реальной практике встречаются три типичных неработающих артефакта:
1. **«Коробки технологий»:** на схеме нарисованы прямоугольники «Kafka», «PostgreSQL», «Redis», «React», но нет ни пользователей, ни границ систем, ни владельцев. Непонятно, кто за что отвечает.
2. **«Схема из классов»:** диаграмма на 150 мелких классов и методов. Это кирпичи реализации, скрывающие за собой саму архитектуру.
3. **«Идеализированные микросервисы»:** красивая топология из 15 квадратиков, создающая ложное впечатление полной автономности, где напрочь забыты внешние платёжные шлюзы, складские системы и реальные вендоры.

Главный критерий любой архитектурной схемы формулируется просто:
> **Какое конкретное инженерное или продуктовое решение (Decision) помогает принять эта схема?**  
> Если ответа нет — схема бесполезна, сколько бы времени на неё ни потратили.

На любой зрелой архитектурной схеме должны быть явно видны 4 элемента:
* **Scope:** чёткая граница проектируемой системы (что строим мы, а что находится снаружи);
* **External Systems:** внешние сервисы и партнёры, без которых система не работает;
* **Ownership:** конкретные команды или роли, владеющие каждой границей;
* **Dependencies:** критичные зависимости и тип связи между ними.

## 2. Модель C4: аналогия Google Maps и тайна 4-й «C» (Code)

Модель **C4**, созданная Саймоном Брауном, предлагает описывать архитектуру так же, как устроены спутниковые карты (Google Maps) — через последовательное приближение масштаба (Zoom):

```text
УРОВЕНЬ 1: System Context (Контекст системы)  ──► Вид на планету / континент
           │
           ▼ (Приближаем масштаб)
УРОВЕНЬ 2: Container (Контейнеры развёртывания) ──► Вид на город / квартал
           │
           ▼ (Приближаем масштаб)
УРОВЕНЬ 3: Component (Компоненты внутри)        ──► Вид на здание / поэтажный план
           │
           ▼ (Приближаем масштаб)
УРОВЕНЬ 4: Code (Классы и методы в коде)       ──► Фотография отдельных кирпичей
```

### Тайна 4-й «C»: почему архитекторы не рисуют уровень Code?
Модель называется **C4**, потому что теоретически включает 4 уровня: Context, Container, Component, **Code**.

Но в профессиональной инженерии **уровень Code осознанно НЕ рисуют на схемах**.
* Код меняется ежедневно с каждым pull request'ом. Диаграмма классов, нарисованная вручную, устаревает уже через 15 минут после публикации.
* Архитектура отвечает на вопрос «как части системы договариваются между собой», а не «какие поля есть у класса `UserHelper`».
* Уровень кода смотрят прямо в IDE или генерируют автоматически, а архитектурное проектирование останавливается на уровне компонентов.

## 3. Сквозной кейс: E-commerce Checkout — System Context

Рассмотрим проектирование оформления заказа (**Checkout**): покупатель выбирает товары в корзине, система проверяет цены, резервирует остатки, проводит оплату и создаёт заказ.

### Уровень 1: System Context View (Контекст системы)

```text
                           [ Покупатель (Customer) ]
                           (Web-браузер / Мобильное приложение)
                                     │
                                     │ Оформляет заказ (HTTPS)
                                     ▼
                      ┌──────────────────────────────┐
                      │  E-COMMERCE CHECKOUT SYSTEM  │ ◄── Наша зона ответственности
                      │  (Проектируемая система)     │     (Scope)
                      └──────────────┬───────────────┘
                                     │
         ┌───────────────────────────┼───────────────────────────┐
         │                           │                           │
         ▼                           ▼                           ▼
[ Catalog & Pricing ]       [ Inventory System ]        [ Payment Provider ]
(Внутренний каталог цен)    (Внутренний склад остатков)  (Внешний платёжный шлюз)
         │                           │
         ▼                           ▼
[ Order Management ]        [ Notification / Identity ]
(Создание заказа)           (Отправка чеков / SMS)
```

### Главные правила System Context:
1. Система показывается как единый чёрный ящик в центре.
2. Вокруг показаны все действующие лица (пользователи) и все внешние системы.
3. **Что категорически НЕЛЬЗЯ рисовать на Context View:** базы данных, серверы, технологии (Docker, Go, React), внутренние таблицы и протоколы вызовов.
4. **Зачем нужен этот уровень:** чтобы согласовать с продакт-менеджером и бизнесом внешние границы и понять: что пишем мы, а от кого зависим.

## 4. Уровень Container View: один контекст — два противоположных решения

Когда граница системы согласована, мы «зумируем» внутрь чёрного ящика Checkout. Мы попадаем на уровень **Container View**.

> **ЖЕЛЕЗНОЕ ПРАВИЛО C4:**  
> **Контейнер в модели C4 — это ВСЕГДА отдельно исполняемый процесс (deployable unit / runtime process) или хранилище данных (data store).**  
> Контейнер — это то, что можно независимо запустить, остановить или развернуть на сервере. Модули, пакеты и классы внутри одного процесса контейнерами НЕ являются!

Один и тот же System Context можно реализовать принципиально разными архитектурными способами:

### Вариант А: Модульный монолит (Modular Monolith)

```text
[ Web / Mobile Client ]
         │ HTTPS / REST
         ▼
┌──────────────────────────────────────────────┐
│ Checkout Application (Контейнер 1)           │ ◄── Единый развёртываемый процесс
│ Внутри: маршрутизация, логика корзины,      │     (Node.js / Go / Java)
│ оркестрация, клиенты склада и платежей       │
└──────────────────────┬───────────────────────┘
                       │ SQL
                       ▼
┌──────────────────────────────────────────────┐
│ Checkout Database (Контейнер 2)              │ ◄── Отдельное хранилище данных
│ PostgreSQL                                   │     (Data Store)
└──────────────────────────────────────────────┘
```
* **Количество контейнеров:** ровно **2 контейнера** (приложение + база данных).
* **Плюсы:** предельная простота развёртывания, ноль сетевых задержек между модулями, локальные ACID-транзакции в БД, дешёвая инфраструктура. Идеальный выбор для стартапов и средних проектов.

### Вариант Б: Распределённая сервисная архитектура (Distributed Services)

```text
[ Web / Mobile Client ]
         │ HTTPS
         ▼
┌──────────────────────────────────────────────┐
│ Checkout API Gateway / Service (Контейнер 1) │ ◄── Приём запросов, авторизация,
│ Независимый веб-сервис                       │     валидация входных данных
└──────────────────────┬───────────────────────┘
                       │ gRPC / Kafka Queue
                       ▼
┌──────────────────────────────────────────────┐
│ Checkout Orchestrator Worker (Контейнер 2)   │ ◄── Фоновый процесс / воркер,
│ Независимый вычислительный сервис            │     управляющий шагами сделки
└──────────────────────┬───────────────────────┘
                       │ SQL / TCP
                       ▼
┌──────────────────────────────────────────────┐
│ Checkout State Store (Контейнер 3)           │ ◄── Хранилище состояний
│ PostgreSQL / Redis Cluster                   │
└──────────────────────────────────────────────┘
```
* **Количество контейнеров:** **3 контейнера**, каждый из которых развёртывается независимо.
* **Цена решения:** появление сетевых задержек, необходимость распределённой трассировки (Tracing), усложнение CI/CD, обработка частичных отказов сети. Оправдано только при высоких нагрузках или независимых командах разработки.

## 5. Уровень Component View: заглядываем внутрь контейнера

Component View показывает внутреннее устройство **ровно одного выбранного контейнера**.

Заглянем внутрь монолитного контейнера `Checkout Application` (из Варианта А):

```text
┌────────────────────────────────────────────────────────────────────────┐
│ Checkout Application (Container)                                       │
│                                                                        │
│  ┌──────────────────────┐         ┌─────────────────────────┐          │
│  │ Checkout API Router  │────────►│  Checkout Coordinator   │          │
│  │ (Приём HTTP-запросов)│         │  (Оркестрация сценария) │          │
│  └──────────────────────┘         └────────────┬────────────┘          │
│                                                │                       │
│              ┌─────────────────────────────────┼──────────────────┐    │
│              ▼                                 ▼                  ▼    │
│  ┌──────────────────────┐         ┌─────────────────────────┐ ┌──────┐ │
│  │ Inventory Adapter    │         │ Payment Provider Client │ │Order │ │
│  │ (Интеграция со       │         │ (Интеграция со шлюзом)  │ │Repo  │ │
│  │  складом)            │         │                         │ │(БД)  │ │
│  └──────────────────────┘         └─────────────────────────┘ └──────┘ │
└────────────────────────────────────────────────────────────────────────┘
```

### Правило экономии мышления: когда Component View избыточен?
> **Component View не является обязательным!**  
> Больше деталей — не значит лучше. Детали, не влияющие на принятие архитектурного решения, должны оставаться в коде.

**Component View не нужен, если:**
1. Архитектурное решение локально и не затрагивает смежные команды;
2. Внутреннее устройство контейнера тривиально (стандартный CRUD-контроллер и сервис);
3. Кодовая база активно рефакторится (схема устареет быстрее, чем её дочитают);
4. Схема не снижает конкретный доказанный риск.

## 6. Сравнительный кейс: Изоляция Payment Processing (PCI DSS)

Как требования информационной безопасности и стандартов регуляторов меняют архитектурные границы?

Рассмотрим индустриальный стандарт **PCI DSS (Payment Card Industry Data Security Standard)**. Он гласит: *любой сервер, через который проходят сырые данные банковских карт (номер карты, срок действия, CVV-код), попадает под тяжелейший и дорогостоящий аудит безопасности*.

### Как это требование меняет System Context и границы?

```text
НЕВЕРНО: Данные карты идут через наш бэкенд (Тяжёлый PCI DSS аудит для всего Checkout!)
Покупатель ──[Номер карты]──► [ Checkout Backend ] ──► [ Payment Provider ]

ПРАВИЛЬНО: Изоляция границы через Hosted Fields / iFrame (Безопасный System Context)
                    ┌──── 1. Ввод карты напрямую в iFrame ────► [ Payment Provider ]
                    │                                                  │
[ Покупатель ] ─────┤                                                  │ 2. Одноразовый
                    │                                                  │    токен карты
                    └──── 3. Оформить заказ с токеном ──► [ Checkout ] ◄┘
```

1. В браузере покупателя поля ввода номера карты рендерятся внутри изолированного **iFrame / Hosted Fields**, принадлежащего непосредственно платёжному шлюзу (Stripe, CloudPayments).
2. Данные карты летят с браузера напрямую на сервера шлюза в обход наших серверов.
3. Шлюз возвращает в браузер безопасный одноразовый токен (`token_xyz123`).
4. Наш Checkout Backend получает только этот токен и отправляет команду на списание: «Списать 1 000 ₽ по токену `token_xyz123`».

**Вывод:** Граница системы Checkout спроектирована так, что серверы Checkout физически не видят номеров банковских карт. Это снижает расходы на безопасность в десятки раз.

## 7. Эрозия архитектурных границ (Boundary Drift)

Нарисовать красивую схему C4 легко. Самое трудное — не дать ей разрушиться в процессе ежедневной разработки. 

**Эрозия границ (Boundary Drift)** — это незаметная деградация архитектуры, когда разработчики ради скорости срезают углы и нарушают спроектированные границы.

### Три главных греха нарушения границ:
1. **Прямой SQL в чужую базу данных (Shared Database Anti-pattern):**  
   Сервис аналитики или складской скрипт лезет напрямую через `SELECT * FROM checkout.orders` минуя API Checkout. Итог: любое изменение таблицы ломает смежные системы без предупреждения.
2. **Обход границы через фронтенд:**  
   Мобильное приложение начинает напрямую опрашивать внутренние базы или микросервисы в обход API Gateway.
3. **Циклические зависимости сервисов (Circular Dependency):**  
   Сервис А вызывает Сервис Б по HTTP, а Сервис Б для выполнения запроса синхронно вызывает Сервис А. Итог: распределённый дедлок и гарантированное падение обоих сервисов при первой же нагрузке.

### Как лид защищает границы:
* Архитектурные фитнес-функции в CI/CD (линтеры архитектуры, например ArchUnit для Java или Dependency-Cruiser для JS/TS);
* Изоляция сетевых контуров и баз данных на уровне прав СУБД (у каждого сервиса свой логин и своя изолированная схема БД);
* Жёсткие межсервисные контракты с версионированием.

## 8. Выбор глубины под аудиторию и стадии компании

Архитектурная схема рисуется не для себя. Она рисуется под конкретную аудиторию:

| Аудитория | Нужный уровень C4 | Какое решение обсуждается |
|---|---|---|
| **Бизнес, Стейкхолдеры, Product** | **System Context View** | Границы ответственности продукта, внешние интеграции, сроки и бюджеты покупки готовых систем |
| **Команды разработки, Смежники** | **Container View** | Протоколы взаимодействия, контракты API, границы развёртывания, зоны дежурства и ownership |
| **Инженер, пишущий код модуля** | **Component View** | Внутренняя архитектура контейнера, выделение адаптеров, подготовка к распилу монолита |

### Достаточная глубина по стадиям компании (Stage-Aware):

| Стадия | Достаточная глубина C4 | Ошибка «Слишком мало» | Ошибка «Слишком много» |
|---|---|---|---|
| **Pre-seed / Seed** | System Context + базовые контейнеры монолита | Нет границ системы и платёжных зависимостей | Проектирование 10 микросервисов для непроверенного MVP |
| **Series A** | Контейнеры с зависимостями, типами связей и владельцами | Команда не знает, кто отвечает за соседние сервисы | Component View для каждого тривиального сервиса |
| **Scale-up** | Межкомандные границы, контракты API, точки интеграции | Локальная схема скрывает риски зависимости от других команд | Детализация каждого облачного ресурса в AWS без фокуса |
| **Corporation** | Ландшафт систем, критические интеграции, аудит безопасности | Пропущены обязательные проверки безопасности и комплаенса | Бюрократическое согласование схем ради галочки |
| **Dividend business** | Зоны легаси, точки изменений, стоимость поддержки систем | Не видна цена изменения устаревших компонентов | Дорогостоящая переписка стабильного монолита на сервисы |

## 9. Чего C4 не решает и 5 типовых ошибок

Чтобы инструмент приносил пользу, нужно чётко понимать границы его применимости:
* **C4 — это не DDD:** C4 показывает структуру развёртывания, но не моделирует доменные агрегаты, инварианты и ограниченные контексты (это задача Блока 4).
* **C4 — это не Data Flow:** C4 не отображает полный жизненный цикл данных, задержки репликации и согласованность (это задача Блока 5).
* **C4 — это не Control Flow:** C4 не описывает сценарии сбоев, сетевые таймауты, ретраи и переходы состояний машины заказов (это задача Блока 5).
* **C4 — это не полный Design Doc:** C4 — визуальная опора архитектурного документа, но не замена описания требований и плана поставки.

### Пять смертных ошибок новичка в C4:
1. **Модули названы контейнерами:** разбиение кода на слои «контроллер-сервис-репозиторий» выдаётся за контейнеры C4.
2. **Смешение уровней детализации:** на Context View появляются таблицы баз данных, а на Container View — детали классов.
3. **Микросервисы как дефолт:** необоснованное нарезание монолита на микросервисы до появления реальной нагрузки или разделения команд.
4. **Скрытые внешние системы:** отсутствие платёжного шлюза или склада на схеме, создающее иллюзию автономности.
5. **Отсутствие команд-владельцев:** сеть квадратиков без указания конкретных команд, отвечающих за поддержку и контракты.

## 10. Алгоритм применения C4 и связь с Блоком 4

При проектировании архитектуры следуйте пошаговому алгоритму из 8 шагов:

```text
1. Назвать решение (Decision) ──► Какую инженерную задачу решаем прямо сейчас?
2. Определить аудиторию       ──► Кто будет читать схему: бизнес, команда или разработчик?
3. Очертить System Context    ──► Нарисовать границы системы, пользователей и внешних партнёров
4. Выбрать Containers         ──► Определить развёртываемые процессы (монолит vs сервисы) и БД
5. Выборочный Component       ──► Детализировать только ключевой контейнер (если необходимо!)
6. Подписать Ownership        ──► Указать команды-владельцы и контракты у каждой границы
7. Проверить глубину          ──► Соответствует ли детальность стадии зрелости компании?
8. Перейти к коду             ──► Зафиксировать архитектурное решение в Design Doc / ADR
```

В следующем, четвёртом блоке нашего курса — **DDD и ownership** — мы сделаем следующий шаг: возьмём спроектированные в C4 контейнеры и наполним их глубоким бизнес-смыслом, защищаемыми инвариантами и моделями данных.
