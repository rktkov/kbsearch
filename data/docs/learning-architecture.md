## 1. Зафиксированные решения

- Курс — общий трек без разделения на Junior/Middle/Senior-потоки.
- Он полезен для широкого диапазона карьерных переходов.
- В первой версии равный баланс трёх результатов:
  1. рабочая инженерная практика;
  2. system design interview;
  3. готовность демонстрировать рост на promotion review.
- Теория: 8 записанных видео по 60 минут.
- Практика: 16 независимых систем.
- Практический семинар: 90 минут — 60 минут design practice + 30 минут discussion/review.
- Баланс индивидуальной и групповой работы — равный.
- Обязательной домашней работы нет.
- Участник может принести собственную рабочую задачу; использование задачи в группе — только по желанию, с обезличиванием чувствительных данных.
- Каждый участник получает индивидуальный `grade-growth report`.

## 2. Входной профиль участника

### Минимальный вход

Участник должен:

- иметь опыт разработки программного обеспечения;
- понимать базовый жизненный цикл feature;
- уметь читать и писать код на рабочем языке;
- иметь базовое представление о API, базах данных и тестах;
- быть готовым объяснять ход своего мышления вслух.

### Не требуется на входе

- знание конкретного облачного провайдера;
- опыт проектирования high-load систем;
- опыт написания RFC или ADR;
- опыт работы в корпорации;
- прохождение system design interviews.

### Входной assessment

До старта участник проходит короткое диагностическое упражнение:

1. получает размытую задачу;
2. задаёт уточняющие вопросы;
3. рисует базовую архитектуру;
4. объясняет одно техническое решение;
5. называет один риск.

Это не экзамен и не фильтр. Его задача — зафиксировать baseline для финального отчёта.

---

## 3. Итоговые способности участника

После курса участник должен уметь:

1. Уточнять проблему до проектирования решения.
2. Разделять требования, решения, ограничения и допущения.
3. Объяснять архитектуру на нескольких уровнях детализации.
4. Выделять границы ответственности и владение данными.
5. Показывать happy path и failure path.
6. Обосновывать trade-offs.
7. Превращать дизайн в план реализации.
8. Связывать тестирование с рисками.
9. Проектировать безопасный rollout и rollback.
10. Рассуждать об эксплуатации и инцидентах.
11. Получать обратную связь и менять решение без потери ownership.
12. Формулировать evidence для следующего грейда.

## 4. Архитектура обучения

Каждый теоретический блок проходит через одну и ту же цепочку:

```text
Concept
  → Document
    → Example
      → Stage-aware comparison
        → Live practice
          → Feedback
            → Growth evidence
```

Домашняя работа не является обязательной частью курса. Основная практика и создание артефактов происходят во время live-сессий.

Если участник приносит собственную задачу, она используется как дополнительный материал для сравнения с учебным кейсом, но не заменяет общий кейс группы.

## 5. Карта теории → практики → артефакта → поведения

| Теория | Основной навык | Практики | Артефакт | Observable behavior |
|---|---|---|---|---|
| 1. PRD | Problem framing | 1–2 | PRD / requirements summary | Задаёт вопросы до предложения решения |
| 2. RFC / ADR | Technical proposal | 3–4 | RFC + ADR | Показывает альтернативы и последствия |
| 3. C4 | Architecture views | 5–6 | C4 overview | Меняет уровень детализации под аудиторию |
| 4. DDD | Boundaries and ownership | 7–8 | Context Map | Не создаёт границы только по техническим слоям |
| 5. Data / Control Flow | Distributed behavior | 9–10 | Flow diagrams + failure table | Проектирует retry, timeout, duplicate и recovery |
| 6. Delivery + Technical Debt | Execution planning and debt management | 11–12 | Plan + RACI + RAID + Debt Register | Объясняет порядок работы, критический путь и цену технических компромиссов |
| 7. Testing / Release | Quality and launch | 13–14 | Test Strategy + Release Plan | Связывает тесты и rollout с рисками |
| 8. Operations | Incident ownership | 15–16 | Runbook + Postmortem | Думает о production до запуска системы |

## 6. Outcomes восьми теоретических блоков

### 1. Problem framing и PRD

Участник может:

- выделить проблему, пользователей и цель;
- сформулировать non-goals;
- превратить расплывчатые слова в проверяемые требования;
- определить P0/P1/P2;
- зафиксировать открытые вопросы и риски.

### 2. RFC, Design Doc и ADR

Участник может:

- выбрать подходящий тип документа;
- сформулировать proposal;
- сравнить минимум две альтернативы;
- описать trade-offs;
- превратить обсуждение в принятое ADR.
- зафиксировать осознанный технический компромисс и условие его пересмотра.

### 3. C4 и архитектурные границы

Участник может:

- построить System Context и Container View;
- объяснить назначение каждого контейнера;
- не уходить в преждевременные детали;
- связать границы системы с требованиями.

### 4. DDD и ownership

Участник может:

- выделить домены и bounded contexts;
- определить владельца данных;
- описать агрегаты и инварианты;
- отличить domain event от integration event.

### 5. Data Flow и Control Flow

Участник может:

- показать путь данных и команд;
- описать состояния и переходы;
- рассмотреть сбои, таймауты, retries и дубликаты;
- объяснить consistency model.

### 6. Delivery planning, tracking и управление техническим долгом

Участник может:

- превратить архитектуру в milestones и epics;
- определить зависимости и критический путь;
- назначить ownership через RACI;
- использовать RAID Log и эскалацию.
- отличать технический долг от обычного feature backlog и дефекта;
- оценить текущую стоимость и будущий риск долга;
- зафиксировать долг в Technical Debt Register;
- определить trigger, owner, priority и Definition of Done для repayment;
- объяснить, какую долю capacity нужно направить на погашение долга.

### 7. Testing, release и launch

Участник может:

- построить test strategy на основе рисков;
- выбрать правильный уровень теста;
- определить go/no-go criteria;
- спланировать rollout и rollback.

### 8. Operations, incidents и postmortems

Участник может:

- определить operational signals;
- описать роли во время инцидента;
- отличить playbook от runbook;
- создать postmortem с владельцами и Definition of Done для действий.

### Сквозной навык: управление техническим долгом

Технический долг не является отдельным списком «плохих задач». Участник учится видеть его как осознанное обязательство, у которого есть:

- причина возникновения;
- текущая стоимость;
- будущий риск;
- владелец;
- trigger для пересмотра;
- приоритет;
- стоимость погашения;
- Definition of Done.

В каждой практике ведущий задаёт вопрос:

> Какой компромисс мы принимаем сейчас и какой долг он создаёт?

В практиках 11–14 этот вопрос становится обязательным элементом review.

## 8. Формат 90-минутной практики

### 00–05 — Briefing

- вводные;
- критерии результата;
- роли участников.

### 05–15 — Requirements discovery

Участник задаёт вопросы и фиксирует ограничения.

### 15–45 — Core design

Участник строит основное решение и объясняет границы.

### 45–60 — Deepening / failure inject

Ведущий добавляет масштаб, ограничение или failure scenario.

### 60–75 — Self-review

Участник сам объясняет сильные стороны, риски и trade-offs.

### 75–90 — Group discussion

- вопросы группы;
- альтернативные решения;
- feedback ведущего;
- фиксация следующего observable behavior.

---

## 9. Индивидуальная и групповая работа

### Индивидуальная часть

- участник в кресле кандидата;
- собственное решение;
- объяснение trade-offs;
- self-review;
- персональный SESSION-RESULT.

### Групповая часть

- reviewers задают вопросы;
- участники предлагают альтернативы;
- группа сравнивает решения;
- ведущий показывает зависимость решения от контекста компании.

Каждый участник должен несколько раз быть кандидатом и reviewer.

---

## 10. Работа с задачами участников

Собственные задачи участников — опциональный дополнительный слой.

Правила:

- задача должна быть обезличена;
- нельзя раскрывать секреты компании, персональные данные и внутренние credentials;
- основная оценка проводится на общем учебном кейсе;
- собственная задача используется для переноса навыка;
- участник может показать PRD, RFC или архитектуру без раскрытия чувствительных деталей;
- ведущий помогает определить, какой документ и навык применим.

---

## 11. Домашняя работа

Обязательной домашней работы нет.

Вместо неё используются:

- работа во время live-сессии;
- короткая фиксация результата в конце занятия;
- добровольная доработка артефакта;
- optional bring-your-own-task;
- повторная попытка на следующем семинаре.

Участник не должен отставать от курса из-за отсутствия времени между встречами.

---

## 12. Финальный capstone

Финальный capstone — live system design interview на новой независимой системе.

Участник должен за ограниченное время:

1. уточнить требования;
2. определить scope;
3. назвать НФТ;
4. показать контекст и крупные компоненты;
5. объяснить data/control flow;
6. назвать trade-offs;
7. разобрать failure scenario;
8. описать rollout и observability;
9. сформулировать следующий шаг реализации.

Финальная оценка сравнивается с входным assessment.

---

## 13. Grade-growth report

Финальный отчёт содержит:

- baseline из входного assessment;
- сильные стороны;
- повторяющиеся паттерны;
- текущие observable behaviors;
- признаки следующего уровня;
- конкретные evidence из 16 практик;
- главные gaps;
- рекомендации для работы и promotion conversation;
- ограничения оценки.

Отчёт не утверждает формальный грейд. Он показывает, какие действия участник уже демонстрирует и какие действия нужно сделать повторяемыми.

---

## 14. Open Decisions

- Размер группы.
- Календарная длительность программы.
- Онлайн / офлайн / смешанный формат.
- Обязательность записи семинаров.
- Точный формат финального отчёта.
- Нужно ли участнику создать полный пакет документов или достаточно отдельных артефактов.
