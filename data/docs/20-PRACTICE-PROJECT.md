# Практика 24.10 · Проект «KBSearch» — смысловой поиск по базе знаний

**Что это:** маленький, но настоящий сервис, который можно собрать за один день и показать вживую за 45 минут.
**Зачем именно он:** это ровно та фича, которая обещана в описании мастер-класса («смысловой поиск по документам на векторной базе»), и на ней видны все пять вопросов и все восемь этапов.
**Корпус:** собственные документы курса (8 теоретических блоков + брошюра + обзор продукта + эта методичка). Бонус: зал задаёт вопрос про методику — поиск отвечает по первоисточнику.

---

## 1. Почему эта фича работает как демо

| Требование к демо | Как фича его закрывает |
|---|---|
| Понятна за 30 секунд | «Найди в методичке, где написано про X» — знакомо каждому |
| Есть настоящая архитектура, но мало кода | ingestion, чанкер, эмбеддинги, векторный индекс, поиск, UI: ~700 строк Go |
| Видны провалы агента | агент не придумает про удаление документа, смену модели эмбеддингов и eval |
| Есть эффектный reveal | тесты зелёные, а `recall@3` низкий — фича не работает |
| Не зависит от интернета в эфире | локальная модель через Ollama, SQLite-файл, никаких API-ключей |
| Можно собрать за день | один бинарник, без Docker и без фронтенд-сборки |

**Название на экране:** `KBSearch` · «Поиск по методичке I Am Lead».

**Почему Go, а не Python.** Аудитория — бэкенд-разработчики, и половина зала пишет на Go. Один бинарник, `go test ./...`, никакого venv и «а у меня не собралось». Плюс это хороший пример: язык не влияет на цикл — PRD, границы, потоки и доказательства одинаковые.

## 2. Пять вопросов — целевые ответы (это же и есть артефакты на экране)

### Q1. Что считаем успехом

| | Формулировка | Кто проверяет |
|---|---|---|
| **Критерий приёмки** | `GET /search?q=…` возвращает 200 и непустой список для 10 загруженных документов | агент, автотест |
| **Успех** | Пользователь находит нужный фрагмент в top-3 и не идёт спрашивать в чат поддержки | пользователь, eval-набор |

**Non-Goals (обязательно на слайде):** генерация ответа LLM, PDF/DOCX, права доступа, мультиязычные запросы, ранжирование по свежести, продакшн-масштаб (>10 000 документов).

**NFR:** p95 поиска < 300 мс на 500 чанках; индекс — один файл; работа офлайн после первого скачивания модели.

### Q2. Из каких частей состоит и кто за что отвечает

| Компонент | Что делает | Владелец (роль) | Инвариант |
|---|---|---|---|
| **Ingestion** | читает файлы, режет на чанки, считает хеши | `indexer` | у каждого чанка есть `doc_id` + `content_hash` |
| **Embedder** | текст → вектор 1024 | `indexer` | одна модель на весь индекс; модель записана в метаданных |
| **Vector Store** | хранит векторы и метаданные (SQLite + `sqlite-vec`) | `storage` | удаление документа удаляет все его чанки в той же транзакции |
| **Retrieval** | запрос → top-k чанков с дедупликацией по документу | `search` | пустой индекс отдаёт `[]`, а не ошибку |
| **HTTP/UI** | одна страница: поле, результаты, подсветка | `web` | — |

Границы проведены по **инвариантам**, а не по папкам: `storage` отвечает за «чанк не живёт без документа», `search` — за «нет дублей документов в выдаче».

### Q3. Куда текут данные

**Путь записи:** `data/docs/*.md` → разбор заголовков → чанк (≤700 рун) → `content_hash` → эмбеддинг → upsert в `vec_chunks` → запись в `documents(status=indexed)`

**Путь чтения:** запрос → эмбеддинг → KNN (`k=12`) → гибридный скор → дедупликация по `doc_id` → top-5 → сниппет

**Что происходит со «смертью» документа:**

| Событие | Поведение | Что видит пользователь |
|---|---|---|
| Документ обновили | хеш изменился → старые чанки удалены, новые вставлены в одной транзакции | ничего, выдача уже новая |
| Документ удалили из папки | `sync` находит `doc_id` без файла → удаляет чанки в той же транзакции | документ исчезает из выдачи |
| Сменили модель эмбеддингов | `embedding_model` в метаданных ≠ текущая → полная переиндексация в новую таблицу, атомарная подмена | ничего, но переиндексация занимает время |
| Упали посреди переиндексации | поиск идёт по последней целой версии; статус `rebuilding` | статус «индекс обновляется» |

### Q4. В каком порядке делать

**5 вех / 9 эпиков.** Каждая задача проверяется без чтения кода.

| Веха | Эпик | Проверяемый результат |
|---|---|---|
| M1 Каркас | E1 Скелет + корпус | `kbsearch stats` печатает 30 документов, 0 чанков |
| M1 | E2 Чанкер | тест: документ на 5 000 рун → ≥6 чанков, у каждого есть `heading` |
| M2 Индекс | E3 Эмбеддинги + хранилище | после `ingest` в `vec_chunks` ровно N строк, N = числу чанков |
| M2 | E4 Синхронизация и удаление | удалили файл → `sync` → чанков этого документа 0 |
| M3 Поиск | E5 API поиска | `kbsearch search "fan-out"` → ≥1 результат с `doc_id=intro-video` |
| M3 | E6 HTTP + UI | одна страница; 3 запроса из демо-набора дают осмысленные сниппеты |
| M4 Доказательства | E7 Eval-набор | `kbsearch eval` печатает recall@3 и MRR по 12 запросам |
| M4 | E8 Тесты отказов | 4 теста: пустой индекс, удалённый документ, битый файл, смена модели |
| M5 Демо | E9 Прогон и запись | 10 запросов подряд < 30 с, offline-запись готова |

**Пример разрезания задачи** (показывается на S37):
> Было: «Реализовать индексацию документов» (2 дня, непроверяемо).
> Стало: «После загрузки 10 документов `kbsearch stats` показывает `chunks == expected`; повторный запуск не создаёт дублей (идемпотентность по `content_hash`)».

### Q5. Как поймём, что работает

| Риск | Доказательство | Чем доказано |
|---|---|---|
| Поиск находит «что-то», но не то | recall@3 ≥ 0.8 на 12 запросах | `kbsearch eval` |
| Удалённый документ остаётся в выдаче | тест `TestDeletedDocNotSearchable` | `go test ./...` |
| Пустой индекс роняет сервис | тест `TestEmptyIndexReturnsEmptyList` | `go test ./...` |
| Смена модели ломает размерность | тест `TestModelChangeTriggersReindex` | `go test ./...` |
| Медленно | p95 < 300 мс на 500 чанках | замер в выводе `eval` |

**Фенс:** «ok» в `go test` — это не доказательство качества, это состояние CI.

## 3. Технические решения (ADR-заготовки для показа)

### ADR-1 · Векторное хранилище: `sqlite-vec`, а не pgvector и не Qdrant
- **Контекст:** демо на ноутбуке, без Docker, индекс ≤ 5 000 чанков, один писатель.
- **Решение:** SQLite + расширение `sqlite-vec`, подключаемое статически через Go-биндинги (`sqlite_vec.Auto()`), один файл `kb.sqlite`.
- **Что теряем:** горизонтальное масштабирование, конкурентную запись, фильтры по метаданным богаче `k` + `rowid`.
- **Когда пересмотрим:** >100 000 чанков или несколько писателей одновременно.
- **План Б:** brute-force косинус в Go по BLOB-колонке (500 чанков × 1024 = ~2 МБ, ~5 мс на запрос). Тогда `store.go` меняется, остальное — нет.

### ADR-2 · Эмбеддинги: локальная модель через Ollama, а не API
- **Контекст:** корпус на русском, эфир без гарантии сети, данные не должны уходить наружу.
- **Решение:** Ollama + `bge-m3` (1024 измерения, хорошо работает с русским), запрос через `POST /api/embed` на `localhost:11434`.
- **Что теряем:** ~1.2 ГБ на диске, нужно поднять демон, латентность выше, чем у in-process модели.
- **Когда пересмотрим:** если recall@3 < 0.7 после настройки чанкинга — пробуем `multilingual-e5` или реранкер.
- **План Б:** `nomic-embed-text` (768) или ONNX через `hugot`, если демон недоступен.

### ADR-3 · Переиндексация целиком, а не инкрементально
- **Контекст:** 30 документов; ожидаем полный `ingest` в десятках секунд на локальной модели *(Assumption — замерить и вписать после сборки)*.
- **Решение:** при изменении модели или схемы — полная переиндексация в новую таблицу, затем атомарная подмена.
- **Что теряем:** время и пиковая нагрузка на эмбеддер; на больших корпусах не годится.
- **Когда пересмотрим:** `ingest` дольше 2 минут.

### ADR-4 · Гибридный скор вместо чистого косинуса
- **Контекст:** эмбеддинги теряют точные термины (`ADR`, `C4`, `fan-out`), а зал будет искать именно их.
- **Решение:** `score = 0.8 * cosine + 0.2 * lexicalOverlap(query, chunk)`, где `lexicalOverlap` — доля термов запроса, найденных в чанке (нормализация по регистру и окончаниям не делается: для демо достаточно точного вхождения).
- **Что теряем:** честную «чистую семантику»; добавляется настраиваемый вес.
- **Когда пересмотрим:** если появится полноценный BM25 — заменить лексическую часть на него.

### ADR-5 · Без LLM-ответа в v1
- **Контекст:** обещание — «находит документ», а не «пишет ответ».
- **Решение:** возвращаем сниппеты, не генерируем текст.
- **Что теряем:** «вау» от ответа; зато нет галлюцинаций и нет лишней зависимости.
- **Когда пересмотрим:** после того как recall стабилен.

## 5. Контракты пакетов

```go
// internal/chunk
type Chunk struct {
	DocID    string
	Heading  string // "C4 → Уровни → Контейнеры"
	Text     string // ≤ 700 рун
	Hash     string // sha1(docID + heading + text)
}

// ChunkDocument режет по заголовкам H1–H3, затем по абзацам.
// Чанк не пересекает границу H2. Длина считается в рунах, не в байтах.
func ChunkDocument(docID, markdown string, maxRunes int) []Chunk

// internal/embed
type Embedder interface {
	EmbedPassages(ctx context.Context, texts []string) ([][]float32, error)
	EmbedQuery(ctx context.Context, q string) ([]float32, error)
	Model() string
	Dims() int
}

// internal/store
func Open(path string, dims int) (*Store, error)
func (s *Store) UpsertDoc(ctx context.Context, docID string, chunks []chunk.Chunk, vecs [][]float32) error
func (s *Store) DeleteDoc(ctx context.Context, docID string) error          // чанки + векторы в одной tx
func (s *Store) KNN(ctx context.Context, q []float32, k int) ([]Hit, error) // sqlite-vec MATCH
func (s *Store) Stats(ctx context.Context) (docs, chunks int, err error)

// internal/index
type Report struct{ Added, Updated, Deleted, Unchanged int }
func Sync(ctx context.Context, docsDir string, st *store.Store, em embed.Embedder) (Report, error)

// internal/search
type Result struct {
	DocID   string
	Heading string
	Snippet string
	Score   float64
	Cosine  float64
	Lexical float64
}
func Search(ctx context.Context, q string, k, top int) ([]Result, error)

// internal/eval
type Metrics struct{ RecallAt3, MRR, P95ms float64; N int }
func Run(ctx context.Context) (Metrics, error)
```

**Схема БД** (метаданные — обычные таблицы, векторы — `vec0` по `rowid`; это самый надёжный паттерн):

```sql
CREATE TABLE documents(
  doc_id TEXT PRIMARY KEY, path TEXT, content_hash TEXT,
  status TEXT, embedding_model TEXT, indexed_at TEXT);
CREATE TABLE chunks(
  id INTEGER PRIMARY KEY, doc_id TEXT, heading TEXT, text TEXT, content_hash TEXT);
CREATE VIRTUAL TABLE vec_chunks USING vec0(embedding float[1024]);
```

- вставка: `INSERT INTO chunks ... RETURNING id` → `INSERT INTO vec_chunks(rowid, embedding) VALUES (?, ?)`
- удаление: `DELETE FROM vec_chunks WHERE rowid IN (...)` + `DELETE FROM chunks ...` в одной транзакции
- поиск: `SELECT c.doc_id, c.heading, c.text, v.distance FROM vec_chunks v JOIN chunks c ON c.id = v.rowid WHERE v.embedding MATCH ? AND k = ? ORDER BY v.distance`
