> Все кейсы Marketplace и Search / Recommendation Feed ниже — **fictional / illustrative cases** курса «I Am Lead». Это не описание реальных компаний, нормативов или production-систем.

## 1. Зачем нужны два потока: миф простой стрелки

В архитектурных обсуждениях часто рисуют простую диаграмму: прямоугольник сервиса А со стрелкой к прямоугольнику сервиса Б (`Сервис А → Сервис Б`). 

Для начинающего разработчика кажется, что система спроектирована. Но на самом деле **одна стрелка скрывает 90% реальной архитектуры**:
* Что именно летит по стрелке: данные, команда на изменение или факт о событии?
* Синхронный это вызов по HTTP или асинхронное сообщение в очереди?
* Кто принимает решение о допустимости операции?
* Какое бизнес-состояние меняется в результате?
* И самое главное: **что происходит, когда сетевой кабель моргнул, и ответ не вернулся?**

Чтобы ответить на эти вопросы, зрелая инженерия разделяет взаимодействие систем на два дополняющих друг друга потока:

```text
┌─────────────────────────────────────────────────────────────────────────────┐
│ DATA FLOW (Поток данных): «Что, куда и в каком виде движется»               │
│ Отвечает за рождение, преобразование, репликацию, кеширование и чтение.     │
│ Пример: «Товар из базы каталога копируется в поисковый индекс Elasticsearch»│
└─────────────────────────────────────────────────────────────────────────────┘
                                      ▲
                                      │ Тесно связаны, но не взаимозаменяемы!
                                      ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│ CONTROL FLOW (Поток управления): «Кто инициирует, кто решает, что меняется» │
│ Отвечает за команды, бизнес-решения, переходы состояний и обработку сбоев.  │
│ Пример: «Покупатель жмёт "Купить" → валидация → оплата → резерв → отправка» │
└─────────────────────────────────────────────────────────────────────────────┘
```

**Mandatory rule:** у каждого критичного бизнес-состояния обязаны быть названы команда-владелец, список допустимых переходов и наблюдаемый путь обработки сбоев (failure path).  
**Recommendation:** начинать проектирование не с монструозной схемы всех систем компании, а с одного конкретного пользовательского сценария и его первоисточника данных.  
**Template:** `../templates/06-data-flow.md` и `../templates/07-control-flow.md` — инструменты структурирования мысли, а не догматичный чертёж.

## 2. Словарь движения данных (Data Flow): 5 ролей ответственности

Прежде чем чертить схемы потоков данных, инженерная команда обязана договориться о терминах. Любое движение данных раскладывается на 5 базовых вопросов:

| Роль | Вопрос для проверки | Пример в коде/архитектуре |
|---|---|---|
| **Producer (Производитель)** | Кто создаёт или изменяет значение? | Продавец в личном кабинете заполняет карточку товара |
| **Consumer (Потребитель)** | Кто читает значение или принимает на его основе решение? | Покупатель в мобильном приложении; сервис рекомендаций |
| **Source of Truth (Источник истины)** | Где живёт канонический факт и кто может его менять? | База данных сервиса каталога (PostgreSQL) |
| **Data Owner (Владелец данных)** | Какая команда отвечает за схему, качество и правила? | Команда Catalog Team (мандат из Блока 4) |
| **Consistency (Согласованность)** | Насколько быстро потребители обязаны увидеть факт? | Строгая (Strong) для цены в чеке; с задержкой (Eventual) для витрины |

### Золотое правило копий и индексов:
> **Read Model, поисковый индекс или кеш в Redis — это всего лишь удобная для чтения копия.**  
> Они не становятся источником истины только потому, что отвечают за 2 миллисекунды. Скорость чтения не даёт права изменять канонический факт.

## 3. Сквозной кейс: Marketplace — путь каталога (Data Path)

Рассмотрим классический путь данных в интернет-магазине: продавец публикует товар (`Listing`), товар становится доступен для поиска, а покупатель оформляет заказ (`Order`).

```text
[ Продавец ] 
      │ 1. Создаёт товар
      ▼
┌──────────────────────────────────────────────┐
│ Listing Context (Source of Truth)            │ ◄── Команда каталога владеет канонической
│ База данных: listing_id, price, title, status│     ценой и статусом товара
└───────┬──────────────────────────────┬───────┘
        │                              │
        │ 2. Асинхронное событие       │ 3. Контракт цены при покупке
        │    об изменении товара       │    (price snapshot contract)
        ▼                              ▼
┌──────────────────────────────┐ ┌──────────────────────────────────────────────┐
│ Search Index (Read Model)    │ │ Order Context                                │
│ Реплика в Elasticsearch      │ │ Фиксирует снимок цены на момент оплаты:      │
│ (может отставать на пару сек)│ │ order_id, locked_price, buyer_id, status     │
└───────┬──────────────────────┘ └──────────────────────────────────────────────┘
        │
        ▼ Читает витрину
[ Покупатель ]
```

### Три вопроса архитектора к каждой стрелке:
1. **Кто владеет фактом?** Если в поиске цена товара 1 000 ₽, а в базе каталога продавец секунду назад изменил её на 1 200 ₽ — какая цена верна? (Верна цена в источнике истины — каталоге).
2. **Что делать при отставании индекса (Stale Read)?** Если покупатель нажал «Купить» по старой цене из поиска, система должна либо тихо продать по зафиксированной цене, либо предупредить: *«Цена товара изменилась, обновите страницу»*.
3. **Где граница фиксации снимка?** Заказ (`Order Context`) обязан сохранить снимок цены (*Price Snapshot*) в своей базе в момент создания сделки, чтобы будущие изменения цен продавцом не меняли сумму уже оплаченного заказа.

## 4. Сравнительный кейс: Search vs Recommendation Feed (Fan-out и задержки)

Зачем нам концепция **Eventual Consistency (согласованности в конечном счёте)**? Чтобы увидеть это, сравним двух потребителей одного и того же события:

```text
                  ┌──► Поисковый индекс (Search Index) ──► Лаг < 2 секунд
[ Изменение товара ]
                  └──► Лента рекомендаций (ML Feed)    ──► Лаг 5–10 минут допустим
```

* **Поисковому индексу** критична высокая свежесть данных. Если продавец снял товар с продажи, а поиск продолжает выдавать его 10 минут, тысячи людей будут кликать по мёртвой ссылке и получать ошибку 404 при попытке купить. Здесь допустимый лаг репликации — считанные секунды.
* **Ленте персональных рекомендаций** (ML-модели, считающие векторные эмбеддинги интересов пользователя) абсолютная свежесть не нужна. Если новый товар появится в блоке «Вам также может понравиться» не мгновенно, а через 10 минут после индексации бэкграунд-воркером — бизнес не потеряет ни рубля.

> **Вывод:** требования к согласованности (Strong vs Eventual) определяются не прихотью инженера, а **бизнес-обещанием пользователю**. Задержка репликации допустима там, где она не разрушает сделку и инвариант.

## 5. Поток управления: Команды, События и Машина состояний (Control Flow)

Если Data Flow показывает статику и движение сущностей, то Control Flow описывает динамику решений.

### Принципиальная разница: Команда vs Событие

| Параметр | Command (Команда) | Event (Событие) |
|---|---|---|
| **Суть** | Просьба выполнить действие в будущем | Свершившийся факт в прошлом |
| **Время глагола** | Повелительное наклонение: `CreateOrder`, `Pay` | Прошедшее время: `OrderCreated`, `PaymentAuthorized` |
| **Можно ли отклонить?** | **Да!** Система может отказать из-за нарушенного инварианта | **Нет!** Факт уже произошёл, его нельзя «отменить» (только компенсировать) |
| **Адресат** | Направлена одному конкретному исполнителю | Публикуется в брокер, её могут слушать 0, 1 или 10 сервисов |

### Жизненный цикл сущности: Машина состояний (State Machine)

В потоке управления состояние сущности меняется строго по правилам конечного автомата:

```text
[ draft ]
    │
    │  Команда: CreateOrder (валидация корзины, снимок цен)
    ▼
[ pending_payment ] ───────────┐
    │                          │
    │  Команда: AuthorizePayment│  Таймаут оплаты (15 минут)
    ▼                          ▼
[ paid ]                  [ cancelled ]
    │                          ▲
    │  Команда: CompleteOrder  │  Команда: CancelOrder (возврат денег)
    ▼                          │
[ completed ] ─────────────────┘
```

### Защита инварианта переходов:
* У каждого перехода есть **Precondition (предусловие)**, **Side Effect (побочный эффект)** и **Observable Result (наблюдаемый результат)**.
* **Запрещённые переходы:** Нельзя принять переход `cancelled → paid`. Если заказ уже аннулирован по таймауту, а платёжный шлюз с задержкой прислал подтверждение списания денег, система обязана заблокировать смену статуса и инициировать процедуру возврата средств (Refund).
* **Где живёт проверка:** Проверка допустимости перехода живёт **строго внутри границы команды-владельца заказа**, а не на фронтенде или в API Gateway.

## 6. Тёмный лес сетевых сбоев: анатомия таймаута и катастрофа дублей

Самая опасная иллюзия начинающего разработчика — уверенность в надёжности локальной сети. В распределённых системах сетевой вызов подвержен фундаментальной неопределённости.

### Анатомия сетевого таймаута (The 3 Scenarios)

Клиент отправляет HTTP-запрос `POST /orders/123/pay` и через 5 секунд получает `504 Gateway Timeout`. Что произошло на самом деле?

```text
Клиент                                               Сервер платежей
  │                                                         │
  ├─── Сценарий 1: Запрос потерялся по пути ───X            │ (Сервер ничего не знает)
  │                                                         │
  ├─── Сценарий 2: Запрос дошёл, сервер упал при записи ───►│ (Падение процесса / OOM)
  │                                                         │
  ├─── Сценарий 3: Сервер СПИСАЛ деньги, но ответ умер ────►│ (ДЕНЬГИ СПИСАНЫ!)
  │    на обратном пути к клиенту ──────────────X           │
  ▼                                                         ▼
```

> **ЖЕЛЕЗНЫЙ ЗАКОН СЕТИ:**  
> **Timeout никогда не является доказательством того, что операция провалилась.**  
> Таймаут означает ровно одно: **СТАТУС НЕИЗВЕСТЕН (UNKNOWN)**.

### Катастрофа двойного клика без идемпотентности
Что делает обычный пользователь, когда видит зависшую крутилку и надпись «Таймаут сети»? Он нервничает и **нажимает кнопку «Оплатить» ещё раз**.
Если бэкенд написан наивно, на сервер придут два запроса. Сервер дважды выполнит списание денег, и у покупателя спишется двойная сумма за один заказ!

### Спасение: Паттерн Idempotency Key (Ключ идемпотентности)

**Идемпотентность** — свойство операции давать один и тот же результат при многократном повторении с теми же входными данными.

```text
Клиент (Фронтенд)                               Сервер заказов / Платежей
       │                                                    │
[Генерирует UUID ключа: idempotency_key=abc-777]            │
       │                                                    │
       ├─── POST /pay (key=abc-777, amount=5000) ──────────►│
       │                                                    │ Проверка в БД: ключ abc-777 есть?
       │                                                    │ НЕТ: Блокируем ключ, списываем деньги,
       │                                                    │ сохраняем результат: status=PAID
       │                                                    │
       │◄── СЕТЕВОЙ ТАЙМАУТ (ответ потерян в пути) ─────────┤
       │                                                    │
[Юзер жмёт кнопку второй раз!]                              │
       │                                                    │
       ├─── ПОВТОР: POST /pay (key=abc-777, amount=5000) ──►│
       │                                                    │ Проверка в БД: ключ abc-777 есть?
       │                                                    │ ДА! Ответ уже сохранён в базе!
       │                                                    │ НЕ СПИСЫВАЕМ ДЕНЬГИ ВТОРОЙ РАЗ!
       │◄── Возвращаем готовый ответ: status=PAID ──────────┤
```

1. **Генерация ключа:** Клиент генерирует уникальный случайный идентификатор операции (`idempotency_key = UUIDv4`) при открытии платёжной формы.
2. **Атомарная проверка:** Сервер при получении запроса проверяет наличие ключа в таблице идемпотентности базы данных.
3. **Защита от дубля:** При повторном запросе с тем же ключом сервер мгновенно возвращает ранее сохранённый ответ без повторного вызова платёжного шлюза.

## 7. Стратегии восстановления и отказоустойчивость (Recovery)

Когда в системе происходит сбой, инженеры применяют системные механизмы самовосстановления:

### Опасность Retry Storm (Шторма повторов)
Если зависимый сервис начал отвечать медленно, а 10 000 клиентов начинают каждую секунду долбить его слепыми повторными запросами (`retry`), они окончательно добивают упавший сервис.
* **Решение:** **Bounded Exponential Backoff + Jitter** (ограниченное число попыток с экспоненциально растущей паузой: 1с → 2с → 4с → 8с, плюс случайный разброс времени, чтобы запросы клиентов не приходили в одну миллисекунду).

### Фоновая сверка (Reconciliation Worker)
Что делать с заказами, которые зависли в статусе `UNKNOWN` после таймаута?
* Создаётся фоновый периодический процесс (**Reconciliation Worker**).
* Раз в 5 минут он находит заказы в статусе ожидания и делает безопасный запрос в платёжный шлюз: *«Каков статус платежа по заказу 123?»*.
* Если шлюз отвечает «Оплачен» — переводим заказ в `paid`. Если шлюз отвечает «Отклонён» — переводим заказ в `cancelled` и освобождаем остатки на складе.

## 8. Сигналы наблюдаемости (Observability)

Поток управления невозможно отлаживать вслепую. Для управляемости системы вводятся сквозные метрики:

1. **Correlation ID (Сквозной идентификатор операции):** уникальный заголовок (`X-Correlation-ID`), который пробрасывается через все микросервисы, очереди сообщений и фоновые воркеры. Позволяет по одному клику в Grafana/Kibana увидеть полную цепочку выполнения одного заказа.
2. **Transition Log (Журнал смены состояний):** неизменяемая таблица аудита: *кто, когда, по какой команде и с какими параметрами изменил статус сущности*.
3. **Replication Lag (Отставание репликации):** метрика времени, показывающая, на сколько секунд или минут поисковый индекс отстаёт от базы данных каталога. Если лаг превышает критический порог — срабатывает инженерный алерт.

> **Главный закон мониторинга:**  
> **Метрика без решения — это просто шум.**  
> Если график в дашборде покраснел, но у дежурного инженера нет понятной инструкции, что делать, — эта метрика бесполезна.

## 9. Контекст стадии компании (Stage-Aware Depth)

Глубина проектирования потоков управления должна быть строго адекватна масштабу компании:

| Стадия | Достаточная глубина потоков | Ошибка «Слишком мало» | Ошибка «Слишком много» |
|---|---|---|---|
| **Pre-seed / Seed** | Один happy path, базовый статус в БД, ручной разбор зависших платежей инженером. | Общая таблица без статусов; деньги списались, а кому принадлежит заказ — неизвестно. | Полномасштабная распределённая сага (Temporal/Camunda) для стартапа из трёх человек. |
| **Series A** | Базовый Idempotency Key для платежей, логирование переходов состояний, алерты на критические ошибки 5xx. | Слепые бесконечные ретраи клиентов, роняющие собственную базу при сбоях. | Корпоративный control plane и сложный circuit breaker на каждый внутренний вызов. |
| **Scale-up** | Сквозной Correlation ID, автоматический Reconciliation Worker, мониторинг лага репликации индексов (SLO/SLI). | Локальные изменения статусов одной командой, ломающие смежные сервисы без предупреждения. | Детализация до секунды каждого второстепенного внутреннего вызова внутри кластера. |
| **Corporation** | Строгий аудит изменений (Compliance), версионирование схем событий, автоматические fallback-сценарии. | Отсутствие логов смены статусов для финансового и юридического аудита. | Бюрократическое согласование любых вспомогательных фоновых джобов и очередей. |
| **Dividend business** | Прагматичные обёртки (Wrapper) вокруг стабильного легаси, безопасный ручной fallback. | Игнорирование стоимости поддержки старых очередей при точечных доработках. | Полная переписка работающего годами процессинга на новую модную архитектуру без ROI. |

## 10. Четыре типичные ошибки новичка в проектировании потоков

1. **Индекс как источник истины:** принятие бизнес-решения об оплате или изменении прав на основе данных из поисковой реплики или кеша вместо канонической базы данных.
2. **Слепые бесконечные повторы (Retry Storm):** зацикленный `while(true) { retry() }` в мобильном приложении или бэкенде, добивающий упавший сервис при первой же аварии сети.
3. **Трактовка сетевого таймаута как отказа:** отмена заказа в базе при получении `504 Gateway Timeout` без процедуры проверки статуса в платёжном шлюзе.
4. **Неидемпотентные финансовые операции:** приём повторных POST-запросов на перевод денег или списание остатков без сквозного Idempotency Key.

## 11. Связь с Блоком 6 (Delivery Planning)

Диаграмма Control Flow — это не просто теоретический рисунок, это **готовая спецификация для декомпозиции задач в бэклог**:

```text
Элемент на диаграмме Control Flow             Задача в Jira / Спринте (Блок 6)
─────────────────────────────────             ────────────────────────────────
Happy Path           ──►    Slice 1: MVP сквозного создания заказа
Проверка ключа идемпотентности         ──►    Slice 2: Middleware валидации Idempotency Key
Обработка сетевого таймаута            ──►    Slice 3: Фоновый воркер сверки платежей (Reconciliation)
```
